# APSGraph 技术白皮书

> 版本：0.8.0
> 更新时间：2026-08-23
> 项目地址：https://github.com/NeverMoreLyh/aps-model-tools

---

## 1. 背景与问题

银行核心系统中，APS（Application Platform System）平台通过 XML 元数据模型定义数据库表结构、交易流程、服务接口、批量任务等。一个完整的银行核心系统通常包含 **500+ 张表**、**数千个模型文件**，分布在多个 Git 仓库中。

在研发和运维过程中存在以下痛点：

| 痛点 | 影响 |
|---|---|
| 模型间引用关系不透明 | 修改一个字段类型或字典定义，无法快速评估影响范围 |
| 模型与数据库 schema 可能不一致 | 上线后发现建表脚本与模型定义有偏差 |
| 生成代码与模型对应关系难追踪 | 模型变更后不知道哪些 Java 类需要重新生成 |
| 功能架构缺乏全局视图 | 模型和代码按什么功能能力组织，缺乏审计手段 |
| 多仓库跨域分析困难 | 模型在业务仓库，生成代码在 ap-parent，消费者在其他仓库 |

APSGraph 正是为解决上述问题而设计的只读分析工具集。

---

## 2. 设计理念

### 2.1 只读安全

工具集 **永不修改源码仓库**，**永不自动执行 DDL**，**永不写入 CodeGraph 数据库**。所有操作都是只读分析，产出报告供人工决策。

### 2.2 紧凑索引

将分散在数千个 XML 文件中的模型结构提取为紧凑的 SQLite 关系索引（V2 Schema），支持高效查询和跨文件引用解析，典型 500+ 表的索引文件约 130MB。

### 2.3 增量友好

基于 SHA-256 文件指纹的增量同步机制，日常开发中只需秒级同步变更文件，无需全量重建。

### 2.4 证据驱动

所有分析结论（影响路径、桥接关系、能力分类）都附带证据来源（文件路径、属性值、注解），可追溯、可验证。

### 2.5 Fail-closed

DDL 生成标注为实验性，遇到无法处理的场景（自定义 DDL 片段、分片表展开等）时以注释告警而非静默跳过。

## 3. 架构设计

### 3.1 整体架构

```
┌──────────────────────────────────────────────────────────┐
│ CLI 入口 (cli.py) │
│ scan / include-deps / import-maven-deps / impact / ddl-gen ... │
├──────────┬──────────┬──────────┬──────────┬──────────────┤
│ scanner │ maven │ store │ impact │ ddlgen │ bridge │
│ (扫描器) │ (索引层) │ (影响分析)│(DDL生成) │ (CodeGraph桥接)│
├──────────┴──────────┴──────────┴──────────┴──────────────┤
│ SQLite V2 关系索引 (.db 文件) │
│ model_files │ nodes │ edges │ scan_state │
└──────────────────────────────────────────────────────────┘
 ▲ ▲
 │ │
 APS XML 源码仓库 CodeGraph SQLite 索引
 (.tables.xml, .parms.xml, (只读查询，不写入)
 .flowtrans.xml, ...)
```

### 3.2 模块职责

| 模块 | 职责 | 行数 |
|---|---|---|
| `scanner.py` | XML 文件发现、解析、节点/边写入、增量同步 | 395 |
| `store.py` | SQLite 连接管理、Schema 初始化、节点查询、引用遍历 | 206 |
| `impact.py` | 变更影响分析（反向 BFS 遍历） | 54 |
| `ddlgen.py` | 批量 DDL 生成（MySQL/Oracle/PostgreSQL） | 676 |
| `ddl.py` | 单表 DDL 预览 | 314 |
| `dbdiff.py` | 模型与实际数据库 schema 差异对比 | 845 |
| `bridge.py` | 模型→生成 Java→CodeGraph 消费者桥接 | 145 |
| `classification.py` | 能力分类审计（34 种功能能力） | 202 |
| `cli.py` | CLI 参数解析与命令分发 | 351 |

### 3.3 SQLite V2 索引设计

**设计目标**：用最少的表结构表达完整的模型关系图。

| 表 | 主键 | 核心字段 | 说明 |
|---|---|---|---|
| `model_files` | id | path, content_hash, parse_status, package_name | 源文件记录 |
| `nodes` | id | stable_id, kind, full_id, raw_id, properties_json | 模型节点 |
| `edges` | id | from_node_id, to_node_id, relation_kind, confidence, evidence_value | 关系边 |
| `scan_state` | id=1 | workspace, completed_at, scanner_version | 扫描状态 |

**关键设计决策**：
- `stable_id`：跨重建稳定的节点标识（`kind:full_id` 格式），用于增量同步时保持引用连续性
- `properties_json`：模型属性以 JSON 文本存储，避免频繁 Schema 变更
- `confidence`：边置信度（CERTAIN / DERIVED），区分直接引用和推导引用
- `evidence_value`：记录引用来源属性值，支持追溯

### 3.4 增量同步机制

```
源码工作空间 SQLite 索引
 │ │
 ├── file A (hash=a1) file A (hash=a0) → MODIFIED
 ├── file B (hash=b1) file B (hash=b1) → UNCHANGED (skip)
 ├── file C (new) — → ADDED
 └── file D (deleted) file D → DELETED
```

同步流程：
1. 扫描工作空间，计算每个文件的归一化相对路径和 SHA-256
2. 与 `model_files` 表比对，分类为 ADDED / MODIFIED / UNCHANGED / DELETED
3. 在单个 SQLite 事务中执行增删改
4. 重新绑定受影响的跨文件引用边

**安全约束**：
- 拒绝遗留 V1 Schema（必须先 scan 重建）
- 拒绝非本工作空间的索引（`scan_state.workspace` 校验）

## 4. 核心能力

### 4.1 变更影响分析

从目标模型反向遍历引用图，回答"谁依赖了我"：

```
BpDict.A.addr (字段变更)
 ← TYPE_REF ← FIELD: SysDbTable.kapp_sundry_busi.amount
 ← WRITES_TABLE ← NAMED_SQL: insert_sundry_busi
 ← CALLS_TRANSACTION ← TRANSACTION: flow_sundry_save
```

输出受影响节点列表、影响路径（按关系类型汇总）、未解析引用（questions）和建议操作。

### 4.2 DDL 生成

逆向自 `apsgraph-util` 的 `DdlGenerator` / `TableDdlUtil` 和 FreeMarker 模板（`mysql.ftl` / `oracle.ftl` / `postgresql.ftl`），实现统一的 DDL 生成器。

**生成管线**：
```
SQLite 索引 → TABLE 节点 → FIELD 节点 → 类型链解析(RESTRICTION_TYPE → baseType)
 → 类型映射(方言) → 长度/精度计算 → varchar→text/clob 转换
 → 索引/主键 → 序列 → 注释(含枚举值) → DDL 输出
```

**与原模板的差异**：
- identity：MySQL 输出 `AUTO_INCREMENT`（原模板输出无效的 `identity`）
- PostgreSQL identity：输出 `GENERATED BY DEFAULT AS IDENTITY`
- 自定义 DDL 片段：不输出，注释告警
- 分片表：按逻辑表名生成，不展开

### 4.3 数据库差异对比

将 APS 模型生成的期望 schema 与实际数据库 schema 逐表对比，按严重级别报告差异。

**对比维度**：表存在性、列存在性、类型族、精度/标度、可空性、默认值、主键、索引、注释。

**两种工作模式**：
- 在线模式：直连 MySQL/Oracle 的 information_schema
- 离线模式：从 JSON 导出文件读取实际 schema（适用于网络隔离环境）

### 4.4 CodeGraph 桥接

将 APS 元数据模型与生成 Java 代码和 CodeGraph 消费者关联：

```
APS 模型 (SQLite 索引)
 → 推导生成 Java 符号 (包名 + 类名 + @ConfigType)
 → 验证 target/gen 文件实际存在
 → 查询 CodeGraph SQLite 找到消费者
 → 输出桥接报告 (JSON)
```

**置信度分级**：
- `CERTAIN_COMPILED`：生成文件存在 + 编译成功 + CodeGraph 索引确认
- `DERIVED`：推导关系，未编译确认
- `GAP`：仓库无 CodeGraph 索引

### 4.5 能力分类审计

基于 34 种功能能力的启发式关键词匹配，将模型和 Java 包按功能维度分类：

| 分类证据来源 | 示例 |
|---|---|
| 模型 ID | `DaySwitchTable` → day-switch |
| 模型描述 | "统一日切功能" → day-switch |
| 文件路径 | `security/encrypt/` → security |
| Java 包名 | `com.sunline.security` → security |
| 类名 | `RedisCacheUtil` → redis |

分类为启发式审计，混合和未分类结果需要人工确认。

## 5. 安全设计

| 维度 | 措施 |
|---|---|
| 源码仓库 | 只读扫描，不修改任何源文件 |
| DDL 执行 | Fail-closed，生成 DDL 不自动执行 |
| CodeGraph | 只读查询，不写入 CodeGraph 数据库 |
| 数据库密码 | `--dsn-env` 从环境变量读取，不进命令行历史 |
| DSN 显示 | 报告中 DSN 自动脱敏（密码替换为 `***`） |
| 索引隔离 | 拒绝非 APS 索引数据库，拒绝跨工作空间索引 |
| Maven 集成 | 构建失败、同一 `groupId:artifactId` 版本冲突、JAR XML 解析失败均不替换已有索引；build 与依赖解析阶段串行，阶段内可并行 |

## 6. 与 dbm2 迁移工具的协作

APSGraph 产出的 SQLite V2 索引可作为 dbm2 数据库迁移工具的可选校准源：

```
APS 源码仓库
 → apsgraph scan --include-deps → SQLite V2 索引 (v87-models.db)
 → dbm2 calibration-sqlite-path 引用
 → 迁移引擎校准类型映射与迁移策略
```

启用校准后，dbm2 迁移引擎在 MySQL → Oracle/TDSQL/GoldenDB 迁移时参考 APS 元数据的类型定义、字段长度、约束等信息，提高类型映射准确性。

## 7. 性能特征

基于 V8.7 银行核心系统（512 张表）的实测数据：

| 操作 | 耗时 | 产出 |
|---|---|---|
| 全量 scan | ~30 秒 | ~130MB SQLite 索引 |
| 增量 sync（10 文件变更） | < 3 秒 | 增量更新 |
| stats | < 1 秒 | 统计信息 |
| impact（depth=3） | < 1 秒 | 影响报告 |
| ddl-gen（全量 MySQL） | ~5 秒 | ~512 张表 DDL |
| db-diff（在线 MySQL） | ~10 秒 | 差异报告 |
| bridge（单模型） | ~2 秒 | 桥接报告 |
| classify（全量） | ~5 秒 | 分类报告 |

## 8. 技术栈

| 维度 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.9+ | 跨平台、快速原型、XML/SQLite 原生支持 |
| 存储 | SQLite | 零配置、单文件、高效只读查询 |
| XML 解析 | xml.etree.ElementTree | 标准库，无需第三方依赖 |
| CLI | argparse | 标准库，统一子命令模式 |
| 运行时依赖 | 无 | 纯标准库实现（db-diff 在线模式可选依赖） |
